# 委譲の単位の共通の決まり(全単位が読む)

この単位は design-doc スキルの Phase 1 の一部だけを書く。SKILL.md(約110KB)は読まない。読むのは、この
ファイルと自分の単位の手順書(prompts/<単位>_*.md)と、手順書が挙げた入力だけ。

## 書く場所と形

- 出力は `target/intermediate/_unit_<単位>.json` の1ファイルだけ(例 `_unit_H2.json`)。partial(`_partial_*.json`)・
  中間JSON・他の単位の断片は書かない。最上位はオブジェクトで、キーは partial と同じ名前(`events`・`api_spec` など)
- 書いてよい欄は、`prompts/units.json` の自分の単位の `owns` だけ。他の単位の欄は空でも書かない(並行に書いている)
- 識別子つきの一覧は、行ごとに識別キーを必ず入れる。他の単位と同じ行を指す手がかりはこの値だけ
  - screen_layout.items=`item_name` / events・event_processes=`event_code` / db_operations=`id` /
    api_spec=`action` / response_items=`key` / request_params=`name` / messages_backend=`message_id`
- 行を作るのは分担表の `creators` の単位だけ。それ以外の単位は、作り手と同じ識別子をソースから導いて欄を足す
  - db_operations の id は `db_op_<action>`。1つの action が複数の SQL を流すときは `db_op_<action>_<n>`(実行順、1から)
  - response_items の key は return する JSON のパスを `rows[].shop_id` の形で1キー1行
  - message_id はソースのメッセージ定義の ID。無ければ MSE(エラー)/MSW(確認)/MSI(通知)+5桁の連番
  - event_code は下書き(`{機能名}_react_draft.json`)の値。下書きが無い画面は EV00 = 初期表示、以降 EV01… を画面の上から順に
- src は書かない。ただし下書きに無い行(ソースを読んで足した行)には、読んだ範囲 {file,line_start,line_end} の配列を書く。下書きにある行は合成が付ける
  - screen_layout.items では、表の行・JSX の入力・ボタン・固定文言の src は合成が下書きから付けるので書かない。カード・表・注記のかたまりなど、下書きに無い構造の項目だけ、読んだ範囲を書く

## 語彙の決まり

- 業務担当者の語彙で書く。関数名・camelCase・CSS クラス名・DB の物理列名・旧システムの物理名
  (project_config の `forbidden_terms_map.terms`)を文に入れない。API の JSON パスと action 名はそのまま
- 括り表記をしない。「各列」「等」「など」「…」や（）・ / で複数をまとめず、1つずつ1行に書く
- 日付時刻の説明文は YYYY/MM/DD HH:MM と書く。形式欄(format)はソースの実形式のまま書く(例 YYYY-MM-DD)。概要の文(最初の1文)は30字以内
- 空のテンプレを作らない。ソースに根拠が無い欄は書かない(推測で埋めない)
- 巨大な api.ts は全文を読まず、`<機能名>_api_excerpt.ts`(下書きと同じフォルダ)を読む
- ボタンや項目の表示名は下書きの `events[].ui_label` を使い、ボタン名を推測しない
- 推測で書いた所は、断片には書かず、終わりの報告の『ソースで判断できなかった所』に書く(断片に notes キーを足さない)

## 事実と根拠の決まり

- 下書きに事実の欄があれば、その値をそのまま使い、言い換えない
  - react 下書き(`{機能名}_react_draft.json`): `initial_fetches`(初期表示で呼ぶ API)・`state_initials`(state の初期値と結ぶ画面項目。`readable` があればそれを使う)・`events[].fetch_plan`(取得が並行か順か)・`csv_exports[]`(`row_builder` と `joins` の並び)・`failure_effects[].failure_state`(取得失敗時に変わる state)・`calc_candidates`(計算式の候補)・`field_usage`(応答項目の出どころ)・`continuous_operation`(連続操作の事実)
  - backend 下書き(`{機能名}_backend_draft.json`): `apis.<action>.db_operations[].columns[]`(`kind`・`real_column`・`alias_name`・`source_columns`)・`apis.<action>.db_operations[].ctes[]`(`name`・`definition`)・`apis.<action>.db_operations[].subqueries[]`(`location`・`definition`・`filtered`)・`apis.<action>.db_operations[].aggregate_units[]`(`func`・`arg`・`alias`・`scope`・`group_by`・`unit`)・`apis.<action>.features.aggregates[]`・`apis.<action>.group_by`・最上位 `common_errors`(`errors[]` の `code_default`・`code_from`・`status_code`)
- 事実の欄に無い内容は、ソースで確かめてから書く。出典の行(src)に無いことを補って書かない。ソースに根拠の無い説明は書かない
- 物理列として書くのは `real_column` だけ。`kind` が `alias_only` の列は `real_column` が空で、`physical_column` に入っている値は別名なので物理列として書かない。別名は `alias_name` のまま別名として書く
- SQL の別名・CTE・副問い合わせは、ソースの書き方どおりに区別して書く。CTE は `ctes[]` の `name` と `definition` のとおりに書き、副問い合わせは `subqueries[]` の `definition` と `filtered`(絞り込みの有無)のとおりに書く。副問い合わせの定義の中の集計は、本体の集計(`aggregate_units` のうち `scope` が `main` のもの)として書かない
- 集計の説明は、`aggregate_units[]` の単位(`unit` = その集計の `group_by` の列。`apis.<action>.group_by` に `when` があれば条件つき)の事実で書く。単位を推測しない。単位が店舗×レジ×日なら「日数」と書かず「店舗×レジ×日の行数」と書く
- API が返すエラーの code は、`error_patterns[].condition` に書かない。`error_patterns[].error_code` に、合成が下書きの最上位 `common_errors` の `errors[].code_default` から機械で入れる。`code_from` は code の出どころで、書く値ではない。`messages_backend[].code` は message_id と同じ MSE 番号(MSE00001 の形)で、API の code は入れない。推測で code や MSE0000x などを作らない
- 例示値は画面の書式に合う実値で書く。ソース(画面の文言・定数・式)に根拠のある例示値は、その字面・計算結果で書く。ソースに根拠の無い例示値(店名・担当者名・金額など実行時のデータで決まるもの)は、「A店」「佐藤」のような思いつきの名前を作らず、型ごとの見本値(日付 2026-10-01、金額 1,234 円、件数・数量 123、比率 12.3%、コード 1)にし、名前・文字列は「実行時の値」と書く(合成が機械でそろえるので、書いた値が違えば直される)。`{金額}` のような穴あきや ○○・XXX は使わない(検査 verify_partials が WARN で差し戻す)
- 断片の最上位に `"meta": {"feature_name": "<機能名>"}` を必ず書く(依頼文の機能名をそのまま)。断片 `_unit_*.json` は機能名に依らない固定名なので、どの画面の断片かをこれで示す。無い・検査の機能名と違うと `[機能名なし]`・`[機能名の食い違い]` の ERROR で差し戻される。meta は設計書の欄ではないので owns には入らない
- 断片を書く担当は WARN を残してよいが、納品の合否では許可リスト(`<機能名>_warn_allow.json`。書き方は `_warn_allow.py` の冒頭)に理由つきで載らない WARN は不合格になるので、WARN の指摘は直せるものを直す。許可リストへの登録は担当ではなくメインが行う

## 終わり方

1. `python3 target/scripts/verify_partials.py --units --unit <単位> --feature <機能名>` を流す(スキルのフォルダで。機能名は依頼文の FEATURE_NAME。無いと検査は止まる)
2. 自分の単位を指す問題(行末「→ 差し戻し先 <単位>」)を直す。他の単位の断片がまだ無いときの照合は飛ばされる
3. 報告は3行まで: 書いた行の数・残った問題・ソースで判断できなかった所
