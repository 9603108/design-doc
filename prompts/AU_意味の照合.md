# AU 意味の照合(haiku。判定項目を1件ずつ、依頼文に載せたソース(全文の節、大きすぎるファイルだけ抜粋の節)と突き合わせる)

## 入力
- 依頼文には、判定項目の前にソースの節が付くことがある。節は2種類で、どちらも行番号つき
  - 全文の節: `==== ソース: <絶対パス>(全 N 行)====` の見出しにファイルの全文が続く。行頭の番号はファイルの行番号
  - 抜粋の節: `==== 抜粋: <項目の id> <絶対パス>(…)====` の見出しに、大きすぎて全文を載せなかったファイルの、その項目が参照する関数・定義の断片が続く(`---- 断片: <名前>(ファイルの <開始>-<終了> 行)----` で区切られる)。行頭の番号は、その節の抜粋の先頭を1とする通し番号(見出し行と断片の見出し行は数えない)。ファイルの行番号ではない
  - 1つの判定項目に全文の節と抜粋の節が混ざってよい(上限内のファイルは全文、超えるファイルだけ抜粋)。どちらの節も、判定の根拠にしてよい
  - 節が付かない判定項目(抜粋の断片を用意できなかったもの)は、`src_excerpt.text` を持つ形で渡る
- メインが渡す判定項目の配列。1件の形は次のとおり
  - `id`: 判定項目の番号(返す行と1対1で結ぶ)
  - `subject`: `statement` が何についての記述か(例: 画面項目「返品」の備考)。文だけでは対象が分からないときの手がかり。判定の根拠にはしない
  - `statement`: 中間JSONの1文(画面・API・DB の記述の1つ)
  - `src_excerpt`(節を載せた項目): `text` を持たず、出典の `file`・`line_start`・`line_end` と、項目の `src_files`(全文の節に載るファイル)・`src_excerpt_files`(その id の抜粋の節に載るファイル。無ければ無い)を持つ
    - 出典の `file` の `line_start`〜`line_end` が主な根拠。`file` が全文の節ならその行。抜粋の節なら、断片の見出しのファイルの行範囲からその行を探す
    - 関数・state・定数・SQL・JSX の定義が別の行にあるときは、この項目の全文の節と、この id の抜粋の節の中から探してよい
    - 抜粋の節の断片は、主抜粋(出典の行の前後)と、主抜粋が呼ぶ関数の本体・state の定義・それを使う hook など(断片の見出しが名前)。`...(以下略)` は行数の上限で切った印で、切れた先を見ないと分からない文は `unknown`
  - `src_excerpt`(`text` を持つ形。節を用意できなかった項目向け): その文の根拠としてメインが切り出したソースの抜粋。`file`・`line_start`・`line_end`・`text` を持つ
    - `text` の先頭は、`file` の `line_start` 付近の主抜粋
    - 主抜粋の後ろに `---- 参照先: <名前> (<ファイル名>:<開始行>-<終了行>) ----` で始まる区切りが続くことがある。主抜粋が呼ぶ関数の本体・state の定義・それを使う hook・文中の `[BE1]` などの定義元・SQL 定数などで、文の根拠はここにもある。区切りの行も1行と数える
    - `[BE1]` などの設計書の ID は、`参照先: [BE1] = <名前> (<メソッド> <パス> action=<action>)` の見出しで、どの処理を指すかが分かる
    - `...(以下略)` は行数の上限で切った印。切れた先を見ないと分からない文は `unknown`

## やること
- 判定項目を1件ずつ読み、`statement` が根拠のソース(依頼文に載せた全文の節と抜粋の節、または `src_excerpt` の `text`)と合うかを判定する
- 正解は、依頼文に載せたソース(全文の節・抜粋の節の両方と、渡した `src_excerpt` の `text`)だけ。載せたソースの外の知識・一般論・業界の慣習では判定しない。載った範囲で確かめられなければ `unknown`
- 判定の基準
  - `ok`: 文の内容が載せたソースと合う
  - `ng`: 文とソースが食い違う(数・条件・順序・対象・出力の値が、ソースと異なる)ときだけ
  - `unknown`: 載せたソースだけでは判断できない(載せたソースの外を見ないと分からない)
- 書き方の好み・言い回しの違い・表現の硬さだけでは `ng` にしない。意味が合っていれば `ok`
- 判断の根拠になった行を `evidence_line` に入れ、その行がどのファイルのものかを `evidence_file` に入れる(下の「出力」の書き分け)
- `reason` は60字以内で、判定の理由を1つだけ書く

## 出力
- 出力は JSON 配列だけ。前置き・後書き・コードフェンス以外の説明文を付けない
- 1件の形は次のとおり。判定項目と同じ数だけ、同じ順で返す
  ```
  {"id": "<判定項目の id>", "verdict": "ok" | "ng" | "unknown", "evidence_line": <整数 または null>, "evidence_file": "<根拠のファイルの絶対パス または null>", "reason": "<60字以内>"}
  ```
- `evidence_line` は、根拠の節の種類で数え方が違う。`evidence_file` には、その節の見出しにあるファイルの絶対パスを書く
  - 全文の節: ファイルの行番号(行頭の番号。`====` の見出し行は数えない)
  - 抜粋の節: その節の行頭の通し番号(抜粋の先頭を1。見出し行と断片の見出し行は数えない。ファイルの行番号を推して書かない)
  - `text` を持つ項目: `src_excerpt.text` の中の行番号(text の先頭行を 1 とする。`line_start` からの行番号ではない)。`evidence_file` は `null`
- 載せたソース(全文の節・抜粋の節・text)で判断できないときは `verdict` を `unknown`、`evidence_line` と `evidence_file` を `null` にする。推測で `ok` や `ng` を埋めない

## 検査
- 返した配列の件数が入力の判定項目の件数と同じであることを確かめる
- 各 `verdict` が `ok`・`ng`・`unknown` のどれかであることを確かめる
- `ng` の件は、`reason` が食い違いの中身(ソースのどの値・条件と文のどこが違うか)を指しているかを読み直す
