# H4 画面ルールとメッセージの写し(haiku)

## 入力
- 画面のソース(入力チェック・計算の式)、バックエンドの validation とメッセージの定義
- `{機能名}_react_draft.json` の `validation_candidates`(kind・field・condition・src。検査・切替・絞り込みの行の候補)
- `07_バリデーション.md`(必要な節だけ)

## 書く欄(`_unit_H4.json`。messages_backend の行を作る)
- `no`(validations_frontend・calculations の通し番号)は書かない。合成が並び順で振る
- `validations_frontend[]`: {field, rule, applied_when, kind, message_id, src}
  - `src` は {file,line_start,line_end} の配列で、その検査・切替・絞り込みをソースで実際に書いている行範囲を全行に書く(入力検査は if/setError/throw の行、表示切替は `{cond && …}` の行、活性切替は `disabled=` の行、絞り込みは `.filter(` の行、API検査は backend 下書きの error_patterns[].src か 400 を返す raise の行)。書かない行は verify_intermediate の check_src が WARN にする
  - field は画面項目の名前(S1 の item_name と同じ字面)。並びは 必須 → 形式 → その他
  - 行の決め方: 候補は react 下書きの `validation_candidates`。候補を1件ずつ清書するか、業務の検査・切替ではない(描画の都合だけの条件)として捨てるかを決め、捨てた候補は書かない。kind は候補の kind を使う(API検査は従来どおり backend 下書きの error_patterns から)。候補に無い画面の検査を足すときは、src にソースの行を書く(候補は行単位の近似で、複数行にまたがる条件は取りこぼすことがある)
  - ソースのチェックを上の決め方で候補から清書する(候補のあるチェックを候補なしで書かない)。field・rule・applied_when を全部空にしない
  - `kind` は処理の種別を次の5つから1つ書く: 入力検査 / 表示切替 / 活性切替 / 絞り込み / API検査
    - 処理の種別を照合する: ソースの書き方で決める。画面で入力値を調べてエラーにする(`if (…) { setError(…) }`・throw・input の required/min/max/pattern/maxLength)だけが 入力検査
    - 条件で表示を出し分ける(`{cond && <…>}`・三項)は 表示切替、`disabled={…}` は 活性切替、`.filter(` で行や項目を絞るのは 絞り込み。表示切替を入力検査と書かない
    - 画面のソースに入力検査が無いときは、kind=入力検査 の行を書かない(画面に無い検査を画面の検査と書かない)
    - **バック側の入力検査(API が入力を調べて 400 で返すもの)は、画面に検査があるかどうかによらず、`kind` を `API検査` にして1件ずつ書く**。backend 下書きの `apis.<action>.error_patterns` で status_code が 400 のものが対象で、1つの message_id ごとに最低1行(検査の漏れは合成後の検査 verify_intermediate が ERROR にする)
      - field は検査の対象の画面項目名(S1 の item_name と同じ字面。`from` → 集計開始日 の読み替え)。rule は下書きの条件と境界(`boundaries`)の事実、applied_when は「API が受け取ったとき…、400 を返す」の形で、画面でなく API 側の検査だと分かるように書く。message_id は下書きの ID(messages_backend の行と同じ)
  - applied_when に「<操作>の取得が失敗したとき」と書く操作は、ソースで API を呼んで取得する操作だけにする(CSV 出力は画面の行を書き出すだけで取得しない。エラーを立てる箇所は catch の中を見て、その箇所を呼ぶ操作を全部書く。検査 check_validation_fetch_operations が ERROR で差し戻す)
  - 入力検査・API検査の rule には境界を、backend 下書きの `apis.<action>.boundaries` と最上位の `common_errors` のとおりに書く。下書きに書いてある事実だけを書き、推測しない
    - 例: shop_id は「正の整数(`v <= 0` は拒否)」、日付(from・to)は「書式 YYYY-MM-DD だけを見る。`impossible_dates_accepted` にある 2026-02-30 のような暦に無い日付も形式検査は通す(暦の検査はソースに無い)」
    - `present: false` の行(order・span_limit)は「開始日と終了日の大小は検査しない」「期間の上限は無い」と、そのまま書く
  - 活性切替・表示切替の画面ルールは、条件に出る state だけを条件にして書く。条件に出ない状態(読込中・エラー)では変わらないときは「〜では変わらない」を1文足す。条件に出ない処理(CSV 出力など)を、その state の説明に書かない
- `calculations[]`: {name, formula, inputs[{name, source}], outputs[{name, destination}], remarks}
  - formula はソースの式を業務の言葉に写す。端数・0 除算・NULL の扱いは remarks
- `messages_backend[]`: {message_id, code, severity, message, emitted_by_api[]}
  - code は message_id と同じ ID(MSE00001 の形)。severity は error / warning / info
  - **severity と ID の接頭辞は対応させる: error=MSE、warning=MSW、info=MSI。連番(5桁)は接頭辞ごとに1から振る**(MSW が1件目なら MSW00001。他の種別の番号を引き継がない)。画面内の警告欄(ポップアップでない注意書き)は warning=MSW。合成が severity から接頭辞と連番を振り直すが、最初から対応させて書く(食い違いは verify_intermediate が差し戻す)
  - **画面の文は、見出し・区切りの「：」も含めて全文を写す**。強調要素の見出し(`<strong>取込欠損の疑い</strong>：この期間に、…` なら「取込欠損の疑い：この期間に、…」)や、前後の固定文を落とさない。src の範囲の画面の文と照らし、欠けていれば verify_vs_source が ERROR(差し戻し先 H4)にする
  - 画面とバックエンドが出すメッセージを全部。S2 の error_patterns の message_id もここに必要
  - `message` はソースの文字列を一字一句そのまま写す。バックの文面は下書きの error_patterns の `text_expanded`(`from は YYYY-MM-DD 形式で指定してください` の形。`validation_error:` などの前置きも `{key}` も画面項目名への言い換えもしない)。下書きの同じ ID の `text_expanded` が複数あれば、文面ごとに1行ずつ書く(`from` と `to` と `shop_id` は別の行)
  - **画面のメッセージ(フロントのソースが出すもの)の可変部は `{項目名}` で書く**(ソースのテンプレートリテラル `${r.status}` → `{status}`。スキーマの例「{項目名}は必須項目です。」と同じ書き方)。例: `（HTTP ${r2.status}）` → `（HTTP {status}）`、`${body.error.code}: ${body.error.message}` → `{code}: {message}`。可変部を語(「HTTP ステータスコード」「エラーコード」)に置き換えない。語にすると固定の文言と区別できず、実行時に何が入るかも読めない。検査 verify_intermediate は messages の `{名前}` を穴として差し戻さない。バック側の文面(下書きの `text_expanded`)は展開済みの文面をそのまま写すので `{key}` を書かない(上の項目のとおり)
  - **文字列を `+` でつないで出す文面は、つないだ全文を1つの message に書く**(例: `(x ?? "ログインの有効期限が切れています") + " — 画面を再読込してください"` → 「ログインの有効期限が切れています — 画面を再読込してください」)。前半だけに削らない。
    - 前半が `body?.error?.message ?? "既定の文言"` のように、サーバーが返す文言を優先し無いときだけ既定の文言を使う形なら、messages は2行に分けて書く。1行目は既定の文言を使う場合(`既定の文言 — …`)、2行目はサーバーが error.message を返した場合(`{message} — …`。可変部は `{項目名}` の書き方。message_id は別の連番、emitted_by_api と src は1行目と同じ)。1行目だけにすると、サーバーの文言が前に付く分岐が設計書から落ちる(messages に remarks の欄は無いので、行を分けて書く)verify_vs_source は `+` と テンプレートリテラルでつないだ全文でソースと照合する
  - 言い換え(「集計開始日が日付の形式でない」)は S2 の condition に書く。message には書かない(ソースの文字列に無い文言は verify_vs_source が差し戻す)
