# S1 画面項目と共通ロジック(sonnet)

## 入力
- 画面のソース(JSX / HTML の全部の入力欄・ボタン・表・表示欄)、screen_config(screen_name・areas)
- `01_画面レイアウト.md`、`13_共通ロジック.md`(必要な節だけ)

## 書く欄(`_unit_S1.json`)
- `no`(items・common_logic の通し番号)は書かない。合成(merge_partials.py --compose-units)が並び順で振る。並び順は画面の上から下・左から右
- `screen_layout.items[]`: {item_name, area_ref, item_type, event_code, format, data_type, length, remarks, example}
  - area_ref・item_type は必須(欠けると検査の [必須] で戻される)
  - screen_no も書かない。add_screen_areas.py が area_ref から areas の screen_no を写す
  - **網羅が仕事**。ソースの画面要素を1つずつ数えて全部挙げる(Haiku はここで 17→12 に減らした)。
    数えた要素の数と items の数を報告に書く
  - item_type は Label / Input / Calendar / TimePicker / Checkbox / RadioButton / FileUpload / TextArea / ComboBox / Button / Grid / Link
  - area_ref は screen_config の areas[].area_no。event_code は react_draft の events の値(操作で動くときだけ)
  - remarks に業務上の振る舞い(既定値・選んだときに何が変わるか)を書く
  - 件数(count)を画面に出す項目の remarks には、数える単位を「<単位>の行数」の形で書く(例: 売上の行数)
  - `example` は全項目に書く。値が実行時に決まる項目(金額・件数・日付・店舗名など)も、画面の書式に合う実値で書く(例 1,234 円、2026-10-01)。`{名前}` の穴・○○・XXX は使わない(検査 verify_partials が WARN で差し戻す)。「（DB の店舗名）」のように括弧の中に DB・データベース・実行時・入力値・任意を書かない(検査が ERROR で差し戻す)。DB 由来の値も実値で書く(例 A店)。店名・店数・日付の例は、ソースの docstring・コメントにある事実(閉店・移転・店数)と食い違う実在らしい値を避ける。事実が分からない店名は「A店」「B店」のような記号名にする
    - 固定文言(ボタン名・見出し・注記など)は、ソースの文字列そのまま。画面に出る全文を書く(子要素の強調・コードの文字も連結する。検査の WARN を避けるために文の一部だけにしない。止まったら全文のまま報告に書く)。Label の固定文の例示値は、合成が出典 src の JSX から画面の字面で付け直す
    - チェックボックスの例示値は状態(オン・オフ)でよい(検査は通す)
    - 表(Grid)の例示値の行数は、下書きの display_rows の `rows_shown`(既定で出る行数。空欄項目 dead を除いた数)と `rows_total`(空欄項目を表示したときの全行数)を使う。自分で数えない。「<rows_shown>行(空欄項目を表示すると<rows_total>行)」の形で書く(合成 _compose_grid_example が同じ文面に付け直す)。全行数を既定の行数として書かない(検査 check_row_count_example が ERROR で差し戻す)
    - 取得エラーの表示の例示値は合成が API のエラーの形から付ける。ソースに無い文言(Failed to fetch など)を作らない。
    - 既定値(日付・件数など)は、下書きの `state_initials` の `readable`(式の意味)に従い、その式で決まる実値を example に書く。式の意味は remarks にも書く(「当月1日」)
    - 例の実値がソースに実在しないと検査 verify_vs_source が止めることがある。止まったら、その行を報告に書く(例の値を理由に行を省かない)
    - 実行時の値を含む文言の例示値は、ソースのコメントに実数があればそれを使う。無ければ上の規則どおり実値を書く
    - 例示値の数(店数など)は、backend 下書きの `docstring_counts` の実数(count)を使う。自分で数えた値や推測の値にしない(検査 check_docstring_count_example が ERROR で差し戻す)
    - 例示値の空白は、react 下書きの `jsx_text_joins` の字面(before・after と gap_before・gap_after)に合わせる。JSX は改行を挟んだ `{式}` の前後に空白を入れないので、「POSがあるのは11店」のように空白を足さない(検査 check_jsx_text_gap が ERROR で差し戻す)
    - ソースの文字列(日付表記を含む)は字面のまま写す。日付の区切りは書く時点でソースに合わせる(合成も直す)
- `screen_layout.diagram_ascii`: 画面の ASCII 図(Mermaid 禁止)
- `common_logic[]`: {name, expression, used_in[], zero_division, null_handling, runs_on}。システム全体で使うロジックだけ
  - `runs_on` は動作場所を project_config の `execution_locations` の語から1つ書く(既定 ブラウザ / サーバー(API) / データベース)。判断の手掛かり: 計算が TSX にあるなら下書きの calc_candidates(`in`)で ブラウザ、SQL の条件・式なら backend 下書きの `logic_candidates`(`runs_on`)で データベース。同じ規則を複数の場所で実装しているときは、場所ごとに別の共通ロジックにする。書かないと検査の [WARN] [動作場所] で戻される
  - 下書きの `logic_candidates` のうち、画面の API が使うもの(`used_by` が画面の API の action を含むもの。サーバー・DB 側のものを含む)は、common_logic に拾う(runs_on はデータベース)。落とすと検査 check_common_logic_dropped が差し戻す(sql_condition は ERROR、表名の対応・列の並びなど部品の定数の sql_fragment は WARN)
  - 画面側の共通の処理も拾う。react 下書きの `logic_candidates`(2か所以上から使う非 JSX の関数。num・fmt・todayJst など。`runs_on` はブラウザ)は、候補ごとに common_logic の1項目にするか、1項目の文に名前で織り込む。src は定義の行(候補の src)。backend の候補だけを書いて画面側を落とさない(検査 check_front_logic_dropped が WARN で差し戻す)
  (この画面だけのロジックは H4 の calculations)。業務ルールを要約して書く(例: 取込欠損の判定のしかた)
  - `processing_steps` は {no, kind, description} の dict の並びで書く(文字列の並びは合成が dict にそろえる)
  - common_logic の src は必ず書く(合成は付けない)。データベース・サーバーで動くものは、条件・定数・関数の定義の行。画面で動くものは、計算する関数の定義の行。
- `events_peripheral[]` / `common_logic_peripheral[]`: 画面の外から来る処理(WebSocket 受信など)があるときだけ

- 表示行(display_rows)の行名は、すべて画面項目(items)の item_name と同じ字面で書く。同じ行名が複数あるとき(小計など)は、item_name を同じ字面のまま複数行書く。区別は remarks に書き、item_name に「（現金計）」のような括弧を付けない
- 共通ロジック章の欄名は description・used_by_processes・processing_steps。読み替え: 上の common_logic の expression・used_in が、それぞれ description・used_by_processes に当たる
- **共通ロジックの description は30字以内の概要を必ず書く**。合成(merge_partials.py)は expression が30字以内のときだけ description へ写し、長い式は processing_steps にだけ入れる(description が空になるので、概要は自分で書く)
- 画面だけの処理（3桁区切りの整形など）と CSV だけの処理は、文の中で「画面では」「CSV では」を書き分ける。下書きの csv_exports[].formats_numbers が false のとき、CSV の値を整形すると書かない

## 書かない欄
- events(H1)、calculations・validations・messages(H4)、screen_layout.areas(screen_config から add_screen_areas.py が付ける)
