# S2 バック処理の業務の説明(sonnet)

## 入力
- バックエンドのソース(screen_config の `backend_files` と、その action の処理が呼ぶ関数)
- `{機能名}_backend_draft.json`(React のとき。apis.<action> の response_items・error_patterns・dataset)
- project_config(`auth`、`forbidden_terms_map`)、画面のソース(レスポンスを画面のどこへ出すかを見るため)

## 書く欄(`_unit_S2.json`。api_spec の行は action、db_operations の行は id で指す。行は作らない)
- `api_spec[].name`(処理名)・`description`(この API が業務で何をするか、30字以内。呼出元の画面の視点は書かない)
- `api_spec[].related_db_operations`(実行する db_operations の id を実行順)・`related_cache_operations`
- `api_spec[].response_items[]` の `transform_backend`(バック側の加工を業務の言葉で。加工しなければ「そのまま」)・`description`
  - key は H3 と同じ JSON パス(`rows[].shop_id` の形)。H3 の key と食い違うと [参照] で戻される
- `api_spec[].response_to_screen_mapping[]`: {api_field_path, screen_item_name, transform}。screen_no は書かない(add_screen_areas.py が screen_item_name から screen_layout.items の screen_no を写す)。screen_item_name は S1 の items の item_name と字面を揃える。transform は写し先の項目(screen_item_name)の動きだけを書き、別の画面要素の語(見出し・副題・ラベル・注記・ボタン)を、写し先の項目名に無いまま書かない(店舗名は副題と一覧に出て、会計カードの見出しには出ない。検査 check_mapping_element_names が ERROR で差し戻す)
  - **必ず書く**(Haiku は一度丸ごと書かなかった)。response_items の key ごとに、画面のソースでどの項目に出るかを辿る。
    screen_item_name は S1 の items[].item_name と同じ字面
  - 写しの行の `transform`(注意: `response_items[].transform_backend` ではなく `response_to_screen_mapping[].transform`)には、同じ表のほかの行と同じく、書式と『値が無いときの扱い(0)』を書く。例「「小計」行(1つ目)に、3桁区切りの数値と「円」で出す。値が無いときは0として出す」。0扱いは、ソース(`num()`・`?? 0` 等)で確かめた列だけに書き、null_as_zero が false の列には書かない。同じキー×画面項目に写しが複数あるときは、表示用の1行に書けばよい(検査 check_transform_zero_fill が WARN で戻す)
  - 選択肢に使う API(店舗一覧など)も同じ。選択欄の項目(店舗)へ結ぶ(選択肢の値・表示名を、それぞれ api_field_path に)。
    渡された画面項目名の一覧に入力欄・選択欄の名前も入っている。api_field_path は response_items の key(`rows[].id` の形)。field_usage の path が画面側の変数名(`shops[]` など)のときは、その変数に入れた API の応答の key に読み替える
  - 画面に出さない API だけ、`response_to_screen_mapping_none_reason` に理由を書き、mapping は空にする(それ以外で空にしない。空だと検査が S2 へ戻す)
- `api_spec[].error_patterns[]`: {condition, status_code, message_id(任意), display(任意)}。condition は業務の言葉で
  (「集計開始日が日付の形式でない」。「from が YYYY-MM-DD でない」と書かない)。下書きの error_patterns を土台にする
  - error_patterns の行は、ソースで起きる条件と返るステータスの行だけを書く(下書きの error_patterns に message_id があれば付ける)。401・403・404・409 など、ソースにメッセージ番号(MSE)の無いエラーも、{condition, status_code, display(画面に出す文があるときだけ)} の行にして error_patterns に書く(message_id は付けない。status_code は整数、condition は業務の言葉で非空。同じ API の message_id つき行と status_code と condition が両方同じにしない)。`db_operations[].remarks` へ逃がさない。処理が無いこと・検査の限界などの注記は行にせず、その API の関連する `db_operations[].remarks` に書く(db_operations に行が無い API は `parameters_backend[]` の該当行の description。api_spec の description は30字以内の概要だけで、注記を書かない)
  - 共通の決まり: DB 障害などの 500 系は、backend 下書きの最上位 `common_errors`(except 節ごとの exception・errors の code_default と status_code)のうち status が取れたものだけを足す。status が空のもの(`via` の補助関数の中で決まるもの)は足さない。status が数値のもの(500 など)は合成が機械で足す(condition は例外名。code は error_code に合成が入れる)ので、同じ status の行を二重に書かない。足りない業務の言い換えが要るときだけ、その status の行を自分で書く。認証切れは下書きの auth に従う
  - 下書きの `apis.<action>.boundaries` の `impossible_dates_accepted`(暦に無い日付)は、その API の関連する `db_operations[].remarks` に「形式検査は桁(YYYY-MM-DD)だけ見る。暦に無い日付(2026-02-30)を弾く処理はソースに無い」と事実だけ書く(error_patterns の行にはしない)。500 の行は合成が足すので書かない。推測で足さない
  - 説明(`description`)に列挙型の引数(集計単位等)の語を書くときは、全選択肢か既定値を添える(一部の選択肢だけを説明に書かない)。30字に収まらないときは、その引数の行(`request_params[]`)の description に全選択肢と既定値を書く(下書きの react の `jsx_elements[].option_texts`(全選択肢)・`default_text`(既定値)を使う。一部だけで足りないときは合成 _compose_enum_description が足す)
  - SQL の文字列の式(例: `COALESCE(x, '(不明:' || …)`)は、`transform_backend` にその文字列を字面どおり書く
  - 本当にエラーを返さない API だけ `error_patterns_none_reason` に理由
- `api_spec[].auth`: 認証の説明(当面この単位。将来 script)。project_config の auth と、ソースの認証の扱いから1文
- `db_operations[].dataset_name`: その DB 操作が何をするかを業務の言葉で(「売上データのある店舗の一覧を取る」)
- `db_operations[].remarks`: その API の注記(処理が無いこと・検査の限界・暦に無い日付の事実など)の置き場。api_spec[].description には書かない(30字以内の検査に掛かる)
- `parameters_backend[]`: {name, type, passed_between[], description}。no は書かない(合成が並び順で振る)

- message_id は下書きのメッセージ ID と展開済みの文面(text_expanded)をそのまま使い、自分で採番しない。文面の言い換え(画面項目名への置き換え)は message ではなく condition にだけ書く
- auth は下書きの auth の事実(project_config の auth と、ソースの認証の扱い)を使う
- 式の欠損の扱い(値が無いときどうなるか)は、その式のソース行を読んだ事実だけを書く。`num()`・`?? 0`・`|| 0` を通らない式に「0 として扱う」と書かない。分からなければ書かない

- 画面項目名(`response_to_screen_mapping[].screen_item_name`)は、渡された画面項目名の一覧の名前をそのまま使う。推測で作らない
- 画面が配列の件数(`{rows.length}`・`${shops.length}`)を表示する所は、react 下書きの `count_displays`(state・units・visible_if・src)にある。件数の写し(`api_field_path` は response_items の配列の key の `rows`(response_items に無い `rows.length` と書かない。検査 [参照] が戻す)、transform に単位と表示条件)は、書かなくてよい。合成(_compose_mapping)が下書きの事実から足す。書くなら `count_displays` の単位(units)の字面で書く(「N件」と書き換えない。検査 check_count_mapping が WARN で差し戻す)
- response_to_screen_mapping は、react 下書きの `field_usage` を土台にする。`rows[].shop_name` のような path ごとに、`uses[].element`(画面のどこで使うか)を screen_item_name に結ぶ。`field_usage` に無い項目を「画面に出る」と書かない

## 書かない欄
- api_spec の method・path・request_params・response_items の no/display_name/data_type(H3)、
  db_operations の dataset・joins・where・order_by(H2)、messages(H4)
- response_items の source(type・source_ref・source_column)・expression・type・src(extract_backend_draft.py の下書きから合成が入れる。書いても残らない)
